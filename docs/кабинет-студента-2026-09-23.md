# Личный кабинет студента

Спецификация от 23.09.2026. Заказана владельцем журнала. Кода ещё нет.

## Зачем

Сейчас обязательные требования (миграционный учёт, виза и пребывание, медосвидетельствование, дактилоскопия и фотографирование, страхование) заполняет менеджер учебного офиса за каждого из 187 студентов, а подтверждающие документы живут вне журнала – в почте и мессенджерах. Кабинет переносит заполнение на самого студента: он вносит данные, прикладывает сканы и видит свою посещаемость.

## Решения владельца

Приняты 23.09.2026 в ходе разбора:

1. Вход – единый вход НИУ ВШЭ (OIDC), не выбор ФИО и не пароли журнала.
2. Порядок проверки зависит от требования: часть студент закрывает сам, часть – только через подтверждение сотрудника. Конкретный список владелец даёт позже; по умолчанию подтверждает сотрудник.
3. Сканы видят: сам студент, его менеджер и полный доступ.
4. Сканы хранятся, пока их не удалят руками; автоматического удаления нет.
5. Студент правит свои документные и бытовые поля; учебные – нет.
6. Посещаемость показывается сводкой и днями по дисциплинам, без имён преподавателей.
7. Язык кабинета – русский. Английский не в первом этапе.
8. Устройство – третья роль в том же приложении, а не отдельный сервис и не подача заявок сотруднику.

## Что уже есть в коде

- Роли `teacher`, `office`, `admin`; вход через выбор ФИО плюс общий пароль (`AUTH_MODE=selection`) и неиспользуемый режим `oidc`, который пускает только записи из `data/accounts.json`.
- Таблицы `student_profiles` (карточка) и `procedures` (требования, статусы «нет данных», «не выполнено», «на проверке», «подтверждено», «не требуется»), справочник требований в `src/office.js`.
- Дневные отметки в `daily_marks` и `daily_revisions`, сводка за период в `src/daily.js`.
- Журнал изменений `audit` с ролью и подписью действия.
- Права: `canSeeStudent` и `canEditStudent` в `src/office.js` – менеджер видит только свои программы и курсы.

## Вход и личность

Вошедший через единый вход ВШЭ сопоставляется с записью реестра **только по внешнему идентификатору**, который заранее проставил учебный офис. Сопоставление по ФИО запрещено: однофамильцы в реестре уже встречались, и ошибка открыла бы чужую карточку.

Новая таблица:

```sql
CREATE TABLE student_accounts(
  externalId TEXT PRIMARY KEY,   -- идентификатор из токена ВШЭ
  studentId  TEXT NOT NULL,      -- запись реестра
  linkedAt   TEXT NOT NULL,
  linkedBy   TEXT NOT NULL       -- кто из сотрудников связал
);
```

Отдельная таблица, а не поле в `roster_students`, потому что обновление реестра из Excel пересобирает записи реестра, а привязка переживать это обязана.

Поведение:

- Учётка связана – сессия получает роль `student` и `studentId`. Роль не выбирается человеком, она следует из привязки.
- Учётка не связана – страница «Ваша учётная запись не связана с записью в журнале, обратитесь к менеджеру» и больше ничего. Ни списка студентов, ни возможности выбрать себя.
- Привязку создаёт и снимает сотрудник (менеджер – в своих программах и курсах, полный доступ – везде). Действие пишется в журнал изменений.
- Идентификатор записи студента производится от ФИО, поэтому переименование студента рвёт привязку. Сотрудник перепривязывает; в журнале изменений это видно.

До подключения OIDC кабинет живёт на демонстрационном входе (`DEMO_MODE=true`): в демо-режиме можно войти студентом из списка. В рабочем режиме этот путь закрыт, как сейчас закрыт `/api/demo-login`.

## Модель данных

**Политика требования.** В справочнике `procedureCatalog` у каждого пункта появляется признак `closedBy`: `"staff"` (итог ставит сотрудник) или `"student"` (студент закрывает сам). По умолчанию `"staff"`. Студент при `"staff"` может довести требование максимум до «на проверке».

**Поля карточки.** В коде появляется список полей, которые студент правит: гражданство, ФИО латиницей, страна направления, дата въезда, основание пребывания, паспорт до, миграционная карта до, проживание, в РФ. Всё остальное (программа, курс, статус контингента, версия программы, куратор, связи с преподавателями) запрос от студента не принимает: сервер сливает присланное с текущей карточкой, беря из запроса только разрешённые поля. Оптимистическая блокировка по версии карточки работает как сейчас.

**Сканы.**

```sql
CREATE TABLE attachments(
  id         TEXT PRIMARY KEY,
  studentId  TEXT NOT NULL,
  kind       TEXT NOT NULL,      -- требование, к которому приложен файл
  fileName   TEXT NOT NULL,      -- как назвал студент, только для показа
  storedName TEXT NOT NULL,      -- имя на диске, производится журналом
  mime       TEXT NOT NULL,
  size       INTEGER NOT NULL,
  sha256     TEXT NOT NULL,
  uploadedAt TEXT NOT NULL,
  uploadedBy TEXT NOT NULL
);
```

Файл лежит на диске: `UPLOAD_DIR/<studentId>/<storedName>`, где `UPLOAD_DIR` задаётся переменной окружения (по умолчанию `data/uploads`). В базе файлы не хранятся: резервная копия базы делается ежедневно и хранится в 14 экземплярах, и сканы раздули бы её в 14 раз.

В данные требования добавляются `submittedAt` и `submittedBy` (`student` или `staff`), чтобы было видно, кто довёл пункт до текущего состояния.

## Экраны кабинета

Три раздела, русский язык.

**Мои требования.** Карточка на каждое требование: текущий статус, срок, поля документа (дата, номер, пояснение), список приложенных сканов, кнопка «Приложить скан». Под каждой карточкой написано, что произойдёт после сохранения: «будет отмечено выполненным» или «уйдёт на проверку в учебный офис». Студент не видит статуса «не требуется» как доступного выбора – освобождение даёт только сотрудник.

**Мои данные.** Редактируемые поля открыты; остальные показаны, но заблокированы с подписью «меняет учебный офис». Так студент видит, что о нём записано, и не пытается править то, что ему не принадлежит.

**Моя посещаемость.** Сверху «Не были N учебных дней» и дата последней явки, ниже – дни с отметками по каждой дисциплине. Имена преподавателей не показываются. Данные только на чтение.

Занятий студент не меняет: адресов для этого у роли `student` не существует, а не спрятана кнопка.

## Адреса

Для студента (все работают только со своей записью, идентификатор берётся из сессии, а не из запроса):

- `GET /api/student/profile` – карточка и перечень полей, которые можно менять.
- `PUT /api/student/profile` – сохранение разрешённых полей с версией.
- `GET /api/student/requirements` – требования с политикой, статусами и сроками.
- `PUT /api/student/requirements/:kind` – данные требования и статус в пределах политики.
- `POST /api/student/attachments/:kind` – приём файла.
- `DELETE /api/student/attachments/:id` – удаление своего файла, пока требование не подтверждено.
- `GET /api/student/attendance?from&to` – сводка и дни по дисциплинам.

Общий адрес выдачи файла `GET /api/attachments/:id` доступен владельцу записи, его менеджеру и полному доступу.

Для сотрудника в карточке студента: список приложенных сканов с датой и автором, открытие файла, подтверждение требования, привязка и отвязка учётной записи.

## Сканы: приём, выдача, удаление

- Принимаются PDF, JPEG, PNG до 10 МБ, не более 10 файлов на требование. Тип определяется по сигнатуре файла, а не по заявленному заголовку.
- Имя файла от студента не участвует в пути: имя на диске производит журнал.
- Папка с файлами не раздаётся веб-сервером. Выдача только через адрес с проверкой прав, всегда как вложение (`Content-Disposition: attachment`), без возможности встроить файл в страницу.
- Каждое открытие файла пишется в журнал изменений: кто, чей файл, когда.
- Удаление ручное. Студент удаляет свой файл, пока требование не подтверждено; после подтверждения – только сотрудник. Автоматической очистки нет по решению владельца.

## Права

Все обращения студента проходят через одно место, которое берёт `studentId` из сессии и подставляет его сам. Обработчик не получает чужой идентификатор из запроса, поэтому «забыть проверку» негде. Роль `student` не получает доступа ни к одному адресу раздела `/api/admin/*` и ни к одному адресу журнала занятий.

## Критерии приёмки

Тесты пишутся до кода:

1. Студент видит только свою карточку, свои требования и свою посещаемость.
2. Обращение студента с чужим идентификатором в теле или пути не возвращает чужих данных.
3. Студент не может изменить программу, курс, статус контингента и связи с преподавателями – эти поля игнорируются, а не вызывают ошибку.
4. Студент не может поставить «подтверждено» требованию с политикой `staff`: максимум «на проверке».
5. Студент не может поставить «не требуется» ни одному требованию.
6. Файл чужого студента не выдаётся; свой – выдаётся как вложение.
7. Файл с подменённым типом (расширение .pdf, содержимое исполняемого файла) отклоняется.
8. Сотрудник видит приложенный скан своего студента; менеджер чужой программы – нет.
9. Преподаватель не получает доступа ни к одному адресу кабинета.
10. В рабочем режиме без OIDC вход студентом недоступен.
11. Каждое действие студента попадает в журнал изменений с ролью `student`.

## Что не входит в первый этап

Английский язык, уведомления студенту (письма и напоминания о сроках), загрузка нескольких файлов пачкой, просмотр сканов прямо в браузере, мобильное приложение, самостоятельная регистрация без привязки сотрудником.

## Открытые вопросы

1. Какие требования студент закрывает сам, а какие уходят на проверку сотруднику. До ответа все помечены `staff`.
2. По какому полю токена ВШЭ сопоставлять учётную запись и как учебный офис получит эти идентификаторы для 187 студентов: столбцом в Excel при обновлении реестра или привязкой вручную при первом обращении студента.
3. Нужен ли сотруднику список «кто ещё не привязан», чтобы отслеживать, кто из студентов не завёл кабинет.

## Зависимости и последствия

- **Единый вход ВШЭ.** Без подключения от ИТ ВШЭ кабинет нельзя включить на сервере. Разработка и приёмка идут на демонстрационном входе.
- **Резервные копии.** Сейчас копируется только база. Файлы сканов требуют отдельного резервирования, иначе копия базы будет ссылаться на отсутствующие документы. Это пункт в инструкции для сервера ВШЭ.
- **Персональные данные.** В журнале появляются изображения документов – это повышает требования к серверу. Вопрос согласуется с ответственным за информационную безопасность ВШЭ вместе с размещением самого журнала.
- **Место на диске.** 187 студентов, пять требований, до 10 файлов по 10 МБ – теоретический предел велик, поэтому в инструкции для сервера указывается наблюдение за размером папки и разумный запас.
