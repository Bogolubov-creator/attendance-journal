# Единый установщик журнала для Windows, Linux и macOS

## Постановка проблемы

Журнал ставят разные люди: владелец на своём компьютере, ИТ-служба ВШЭ на сервере университета. Сейчас есть два отдельных скрипта – для Linux и для Windows – с разной логикой, и оба ставят журнал только на ту машину, где их запускают. ИТ-службе удобнее ставить на Linux-сервер со своего рабочего компьютера (часто Windows) по SSH, а этого нет. Повторный запуск спрашивает, перезаполнить ли настройки, вместо того чтобы распознать прежнюю установку и предложить обновление. Своего HTTPS-прокси у сервера compose-конфигурация не допускает: Caddy запускается всегда. После появления личных паролей установщик по-прежнему предлагает общий пароль как основной способ входа, хотя на новом сервере переходный период не нужен.

ТЗ от владельца (файл «Техническое задание: интерактивный установщик») требует: `install.sh` и `install.bat` с общим сценарием, одинаковыми вопросами и проверками; установка на удалённый Linux-сервер по SSH; проверки до изменений; обнаружение прежней установки со сценарием обновления; безопасное поведение при ошибках. Владелец решил совместить ТЗ с уже сделанным: установка прямо на Windows и без Docker сохраняется.

## Решение

Один интерактивный установщик на Node.js 24 с одинаковыми вопросами на всех системах; `install.sh` (Linux и macOS) и `install.bat` (Windows) – короткие обёртки, `install.ps1` тоже остаётся обёрткой, чтобы прежние команды работали. Установщик ставит журнал на этот компьютер (через Docker или без Docker) или на удалённый Linux-сервер по SSH (только Docker). Сам он ничего в систему не ставит – ни ОС, ни Docker, ни Node.js: проверяет и объясняет. Способ входа по умолчанию – личные пароли, свежая установка сразу работает только по ним; в конце установщик выдаёт первый код приглашения администратору журнала.

## Как выглядит готовое

**Запуск.** В папке журнала человек запускает `./install.sh` (Linux, macOS) или `install.bat` (Windows, двойным щелчком или из командной строки). Если нет Node.js 24, обёртка сразу пишет, где его взять, и останавливается. Дальше вопросы идут по одному; у каждого – короткое пояснение и ответ по умолчанию в квадратных скобках, Enter принимает его, ввод `<` возвращает к предыдущему вопросу.

**Куда ставить.**
1. «На этот компьютер» или «На удалённый Linux-сервер по SSH».
2. Для удалённого: адрес сервера, пользователь, порт (22), путь к ключу (пусто – ключ по умолчанию), папка установки на сервере. Пароль SSH, если нужен, спрашивает сам SSH – установщик его не видит и не сохраняет. Установщик проверяет, что сервер отвечает по SSH, что это Linux и что на нём есть Docker с Compose и права пользователя на Docker.
3. Для этого компьютера: «Через Docker» или «Без Docker». Без Docker – на Linux служба systemd, на Windows задача планировщика при старте системы; на macOS – только Docker (установщик так и пишет).

**Проверки до изменений.** Папка журнала (есть исходники), Node.js 24, Docker и Compose (для Docker), права (на Windows – PowerShell от имени администратора для способа без Docker; на Linux – не root, с sudo), свободные порты 80 и 443, если выбран встроенный Caddy. Любая ошибка – понятное сообщение, что сделать, и остановка; к этому моменту ничего не изменено.

**Прежняя установка.** Если в целевой папке уже есть `.env` или база журнала, установщик останавливается и предлагает «Обновить» или «Выйти». «Обновить»: копия базы с датой в имени, новый код (для удалённого – новый архив), пересборка и перезапуск; `.env`, база, сканы, резервные копии остаются как были; в конце – та же проверка здоровья. Перезаполнить настройки заново можно только отдельным ключом запуска и после подтверждения; прежний `.env` сохраняется копией.

**Вопросы о настройке (новая установка).**
- Домен сайта (проверка формата); адрес сайта – `https://домен`.
- Встроенный Caddy (сертификат сам, порты 80 и 443) или свой прокси. Для своего – сколько прокси стоит перед журналом (`TRUST_PROXY`, по умолчанию 1) и предупреждение: прокси обязан передавать заголовок Host без изменений.
- Способ входа: «Личные пароли» (по умолчанию) или «Только общий пароль». Для общего – предупреждение, что он не подтверждает личность и требует ограничить доступ к сайту; пароль вводится скрыто и дважды, в настройки попадает только хеш.
- Папки базы, резервных копий и сканов (по умолчанию `data`, `backups`, `uploads` в папке журнала для Docker; `data`, `data/backups`, `data/uploads` без Docker).
- Сколько резервных копий хранить (14).
- Сводка выбранного без секретов и вопрос «Установить?».

**Установка и запуск.** Установщик создаёт `.env` с закрытыми правами, готовит папки, для удалённой установки копирует на сервер архив только из файлов репозитория (без `.env`, баз, выгрузок и копий), проверяет конфигурацию, собирает и запускает журнал, ждёт ответа `/healthz`. Затем проверяет сайт по HTTPS; если сертификат ещё не получен или домен пока не указывает на сервер – предупреждение с объяснением, установка при этом считается успешной. Если журнал не стал здоровым – последние строки журнала сервера на экране, `.env` и данные остаются для диагностики, ничего не удаляется, код выхода – ошибка.

**Личные пароли.** Свежая установка сразу работает в режиме «только личные пароли»: общий пароль не спрашивается, выбора себя из списка на экране входа нет. В конце установщик спрашивает, кому из сотрудников полного доступа выдать первый код (по умолчанию Гаджиева), и показывает логин и код.

**Памятка в конце.** Адрес сайта; как смотреть журнал сервера и перезапускать; где база, сканы и копии; что копии базы не включают сканы и обе папки нужно выгружать на внешнее хранилище вместе; как загрузить реестр на сайте («Студенты» → «Обновить реестр из Excel»); как выдать коды остальным; как обновить журнал (снова запустить установщик). Для режима «только общий пароль» – напоминание, что он не подтверждает личность и перед реальными данными доступ к сайту нужно ограничить.

## Критерии приёмки

К1. `install.sh` (Linux, macOS) и `install.bat` (Windows) запускают один и тот же установщик с одинаковыми вопросами и проверками; прежние команды запуска `scripts/install.sh` и `scripts/install.ps1` продолжают работать; без Node.js 24 обёртка сообщает, где его взять, и останавливается.

К2. Первый вопрос – куда ставить: на этот компьютер или на удалённый Linux-сервер по SSH. Удалённо – только через Docker; на этот компьютер – через Docker или без Docker (Linux – служба systemd, Windows – задача планировщика; macOS – только Docker, с объяснением).

К3. До любых изменений установщик проверяет: папку журнала, Node.js 24, Docker и Compose (если нужен), SSH-доступ, Linux и Docker на удалённом сервере, права, свободные порты 80 и 443 при встроенном Caddy. При ошибке – понятное сообщение и остановка, файлы не изменены.

К4. У каждого вопроса есть пояснение и ответ по умолчанию; Enter принимает его, ввод `<` возвращает к предыдущему вопросу с сохранёнными ответами.

К5. При найденной прежней установке (есть `.env` или база в целевой папке) установщик предлагает только «Обновить» или «Выйти». «Обновить» делает копию базы, ставит новый код, пересобирает и перезапускает; `.env`, база, сканы и резервные копии не меняются. Перезаполнить настройки можно только отдельным ключом запуска с подтверждением, прежний `.env` сохраняется копией.

К6. Созданный `.env` содержит домен, `APP_ORIGIN` с `https://` на этом домене, `DEMO_MODE=false`, `DATA_MODE=live`, способ входа, `TRUST_PROXY`, число копий и пути папок; на Linux и macOS права 600, на Windows доступ только администраторам и системе. Значения с переводом строки или пустые обязательные значения отклоняются до записи; секреты не выводятся на экран.

К7. При способе «Личные пароли» (по умолчанию) свежая установка сразу работает в режиме «только личные пароли», общий пароль не спрашивается. При способе «Только общий пароль» установщик предупреждает, что он не подтверждает личность, спрашивает пароль скрытым вводом дважды, в `.env` записывает только хеш; пароль не попадает ни в аргументы команд, ни в вывод.

К8. Удалённая установка копирует на сервер архив только из файлов репозитория – без `.env`, баз, выгрузок, копий и папок данных; `.env` создаётся на сервере; сборка и запуск выполняются там.

К9. При своём прокси встроенный Caddy не запускается, журнал доступен только на `127.0.0.1:3100` сервера, установщик спрашивает `TRUST_PROXY` и предупреждает о передаче заголовка Host.

К10. Пути к папкам базы, копий и сканов задаются при установке и соблюдаются и при установке через Docker, и без него.

К11. Установка проверяет конфигурацию, собирает и запускает журнал и ждёт ответа `/healthz`. Если журнал не стал здоровым, установщик показывает последние строки журнала сервера, оставляет `.env` и данные, ничего не удаляет и завершается с ошибкой.

К12. После успешного запуска установщик проверяет сайт по HTTPS; неудача даёт предупреждение с объяснением, а не ошибку.

К13. В конце новой установки установщик спрашивает, кому из сотрудников полного доступа выдать первый код (по умолчанию Гаджиева), показывает логин и код и печатает памятку: адрес, логи, перезапуск, где данные, копии вместе со сканами, загрузка реестра на сайте, выдача кодов остальным, обновление.

К14. Ошибки SSH, Docker, домена, портов и проверки здоровья дают понятное сообщение с тем, что сделать, и безопасную остановку.

К15. INSTALL.md описывает новый установщик: все сценарии (этот компьютер через Docker и без, удалённый сервер по SSH), обновление, требования и частые ошибки.

## Решения по реализации

- **Ядро установщика – один модуль на Node.js 24** без внешних пакетов: вопросы через `readline` (скрытый ввод пароля – через отключение эха в терминале), команды – через `child_process`. Ядро разделено на чистую часть (шаги вопросов со значениями по умолчанию и проверками, навигация «назад», сборка содержимого `.env`, обнаружение прежней установки, план команд для выбранного сценария) и исполнитель, который выполняет план. Ввод и запуск команд передаются в ядро снаружи – так ядро проверяется тестами без Docker, SSH и systemd.
- **Обёртки:** `install.sh` в корне (bash) и `install.bat` в корне (cmd) проверяют Node.js 24 и запускают ядро, передавая ключи запуска. Существующие `scripts/install.sh` и `scripts/install.ps1` превращаются в обёртки над тем же ядром (прежние ключи `--docker/--native`, `-Docker/-Native` сохраняют смысл «этот компьютер через Docker / без Docker»).
- **Ключи запуска:** выбор сценария без вопросов (этот компьютер через Docker, без Docker, удалённый сервер), обновление, перезаполнение настроек (только с подтверждением).
- **Сценарий «этот компьютер без Docker»** переносит поведение нынешних скриптов: Linux – служба systemd с ограничениями (пишет только в папки данных); Windows – задача планировщика от имени SYSTEM при старте системы с перезапуском при сбое, закрытые права на папки данных и `.env`. Для задачи Windows команды PowerShell вызываются из ядра через `powershell.exe -NoProfile`.
- **Удалённый сценарий:** системные `ssh` и `scp` (OpenSSH встроен в Windows 10+ и в Linux/macOS), опции `-p`, `-i`, `BatchMode` для проверок. Архив – `git archive HEAD`, а если папка не под git – `tar` по списку файлов приложения (исходники, публичные файлы, скрипты, `package*.json`, `Dockerfile`, `.dockerignore`, `compose.yaml`, `deploy/`, `.env.example`). `.env` формируется локально в памяти и передаётся на сервер через стандартный ввод SSH с правами 600, без временного файла на локальном диске и без аргументов командной строки. Команды на сервере – `docker compose` в выбранной папке.
- **Обнаружение прежней установки:** в целевой папке (локальной или на сервере) есть `.env` или файл базы журнала.
- **Обновление:** копия базы через `sqlite3 .backup` там, где он есть, иначе копия файла базы при остановленном журнале; затем новый код, `docker compose up -d --build` или `npm ci --omit=dev` и перезапуск службы или задачи.
- **compose.yaml:** встроенный Caddy выносится в профиль, который включается только при выборе встроенного прокси; при своём прокси журнал публикуется на `127.0.0.1:3100`. Пути папок данных передаются переменными из `.env` со значениями по умолчанию `./data`, `./backups`, `./uploads` – прежний запуск `docker compose up` без переменных работает как раньше.
- **Режим «только личные пароли» при свежей установке** включается тем же флагом в базе, что и кнопка дня переключения: установщик после первого успешного `/healthz` вызывает серверный скрипт, который ставит флаг (новый небольшой скрипт по образцу `allow-shared-password.mjs`, работает с файлом базы). Общий пароль в этом случае не задаётся (`MANAGEMENT_PASSWORD_HASH` пустой).
- **Первый код** выдаётся существующим `scripts/invite-admin.mjs` (для Docker – через `docker compose exec app`, удалённо – через SSH); список сотрудников полного доступа берётся из справочника журнала.
- **Проверка портов 80 и 443:** попытка занять порт локально или `ss`/`netstat` на удалённом сервере; занятый порт при встроенном Caddy – ошибка с предложением выбрать свой прокси.
- **Проверка HTTPS:** запрос `https://домен/healthz` с таймаутом; неудача – предупреждение.
- **Проверка здоровья:** до 60 секунд ожидания `/healthz` с заголовком Host домена; при неудаче – последние 50 строк журнала (`docker compose logs`, `journalctl` или `data/server.log`).
- **Новые зависимости и внешние сервисы: не вводим.** Node.js 24 уже требуется журналом; `ssh`, `scp`, `git`/`tar`, `docker` – системные программы, которые установщик только проверяет.

## Решения по тестированию

- Хороший тест проверяет, что установщик спросил, что записал в `.env` и какие команды собрался выполнить в каком порядке, – а не внутреннее устройство шагов.
- **Основной шов – ядро установщика с подменённым вводом (очередь ответов) и подменённым запуском команд** (записывает вызовы и отдаёт заранее заданные ответы), по образцу существующих тестов на `node:test`. Им покрываются: вопросы и ответы по умолчанию, шаг «назад», проверки и сообщения об ошибках (нет Docker, нет SSH, порт занят, плохой домен, перевод строки в значении), содержимое `.env` для каждого сценария, план команд для этого компьютера (Docker, Linux без Docker, Windows без Docker) и для удалённого сервера, обнаружение прежней установки и сценарий обновления, отсутствие секретов в выводе и аргументах команд, поведение при неудачном `/healthz` (ничего не удаляется), предупреждение при неудачном HTTPS, выдача первого кода.
- **Второй шов – существующие HTTP-тесты журнала** для серверного скрипта включения режима «только личные пароли» (по образцу теста `allow-shared-password.mjs`).
- **Обёртки** проверяются запуском на машине разработчика: `install.sh` на macOS; `install.bat` и ветка Windows – разбором и прогоном ядра под PowerShell 7 с подменой команд, как для нынешнего `install.ps1`. Живой прогон на Windows, Linux-сервере с Docker и по SSH – ручная проверка перед передачей в ИТ, в тестах не автоматизируется.
- Прецеденты: тесты серверных скриптов в `staff-first-login.test.js` и `staff-personal-only.test.js`; подмена ввода – как в `tests/ui-access.test.js`.

## Вне рамок

- **Вход через ВШЭ (OIDC) в установщике** – решение владельца: параметры от ИТ ещё не выданы, а для первого администратора нужен его идентификатор ВШЭ, которого до первого входа никто не знает. Режим остаётся в коде и настраивается вручную по DEPLOY.md.
- **Загрузка реестра при установке** – журнал принимает при первом запуске только `roster.json`, реестр из Excel загружается на сайте; установщик показывает этот шаг в памятке.
- **Установка ОС, Docker, Node.js и настройка сети** – установщик только проверяет и объясняет (так требует ТЗ).
- **Установка на удалённый сервер без Docker и на удалённый Windows-сервер** – удалённо только Linux с Docker.
- **Служба без Docker на macOS** – на macOS только Docker.
- **Скачивание кода сервером с GitHub** – решение владельца: код уезжает архивом из локальной копии.

## Прочие заметки

- ТЗ владельца предполагало, что Windows – только машина, с которой ставят; по решению владельца установка прямо на Windows (без Docker и через Docker Desktop) сохраняется.
- ТЗ предлагало выбор «OIDC или общий пароль» и отдельно советовало «подключить индивидуальную авторизацию» – она уже есть (личные пароли), поэтому стала способом по умолчанию.
- Рабочий сервер владельца на Mac запущен вручную (`node --env-file=.env.server`) в демо-режиме за шлюзом; установщик его не трогает, и его «обновление» этим установщиком в рамки не входит.
- Файл `install.ps1` должен оставаться в UTF-8 с BOM и CRLF (Windows PowerShell 5.1), `.bat` – в кодировке, которую cmd читает корректно (только ASCII в самом `.bat`, русский текст выводит ядро на Node.js).
